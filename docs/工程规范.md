# 絮语工程规范

这份规范写给以后维护絮语的每一个 AI 和人。目标只有一个：任何人接手，都能按同一套写法改代码，改完不坏别的地方。

## 0. 怎么用

- 改絮语的任何代码之前，先读完这份规范。规则有编号（如 DATA-3），审查报告和提交说明里引用编号。
- 标着「现状」的是现在的代码还没做到的地方。新写的代码必须照规则写；碰到旧代码时，只在这次改动本来就要动的范围里顺手对齐，不要为了对齐规范去大面积改没让你改的代码。
- 规范和用户当面说的要求冲突时，以用户为准，并在同一次提交里更新这份规范（先问用户）。
- 规范没写到的情况：照着周围代码的写法来；拿不准就问用户，不要猜。

## 1. 项目地图

| 位置 | 管什么 |

## 2. 架构分层（ARCH）

- **ARCH-1　依赖方向**：`Core` ← `Models` ← `Services` ← `Views`。下层不能引用上层的类型：Service 里不能出现 View 类型；Models 里不能调用 Service。
- **ARCH-2　全局状态**：会被界面观察的服务，写成 `@MainActor @Observable final class`，在 `XuyuApp` 里创建一次，用 `.environment(...)` 注入（参照 `RelayClient`、`ChatEngine`、`Router`、`BannerCenter`）。不需要被观察的内部状态加 `@ObservationIgnored`。
- **ARCH-3　单例**：`static let shared` 只用于整个进程只能有一份的系统资源（音频播放、定位、App 锁这类）。新的业务服务不要再写成单例，用 ARCH-2 的注入方式。
  现状：`Books`、`Thoughts`、`MomentsEngine`、`ListenTogether`、`VideoCards`、`CallLogs`、`DiaryState` 等是单例，以后重构时逐步改。
- **ARCH-4　无状态的逻辑**：只是一组函数、不持有状态的，写成 `enum Xxx { static func ... }`（参照 `Backup`、`Companion`、`World`）。
- **ARCH-5　界面里不写业务**：View 里只做展示、`@Query` 读取和简单的增删改。网络请求、拼提示词、计时、复杂的数据处理都放进 Service。
- **ARCH-6　按功能拆文件**：一个文件放一个主要类型。同一个类型的不同功能用扩展拆开，文件名用 `类型+功能.swift`（参照 `ChatEngine+Recover.swift`）。
- **ARCH-7　文件大小**：一个文件超过 500 行就该考虑拆分。新功能不要继续往已经超过 500 行的文件里塞，新开文件。
  现状：`VoiceViews`、`ChatEngine`、`ChatView`、`VoiceCall`、`MomentsView`、`RelayClient`、`Composer` 超过 500 行。
- **ARCH-8　依赖库**：App 不引入第三方库；中继只依赖 `ws`。加任何依赖都要先问用户。

## 3. 命名与注释（NAME）

- **NAME-1**：标识符用英文，遵守 Swift API Design Guidelines。类型用大驼峰，其余用小驼峰，布尔值读起来像判断（`isGroup`、`canWork`）。
- **NAME-2**：注释用中文。每个类型、每个含义不明显的属性和函数，都要有 `///` 文档注释，说清楚它对用户意味着什么、为什么这样做，而不是复述代码（参照 `Persona` 的属性注释）。
- **NAME-3**：分区用 `// MARK: - 中文名`。
- **NAME-4**：改了代码就同步改注释。过时的注释比没有注释更坏。
- **NAME-5　选项用枚举**：有几种取值的设置，用 `enum Xxx: Int` 或 `enum Xxx: String`，不要用裸的 `Int` 编码。
  现状：`proactiveFreq`、`followUp`、`voiceFreq`、`momentsFreq` 用 `Int` 加注释表示。新代码不要照抄，旧的在动到时改成枚举的计算属性（存储字段不变，见 DATA-4）。
- **NAME-6**：同一个东西在代码、界面、注释里用同一个名字。术语以界面上的叫法为准：角色、动态、中继、心声、世界观、一起听、一起读。

## 4. 数据与持久化（DATA）

- **DATA-1　存在哪里**：
  - 用户内容和互相有关联的数据 → SwiftData（`App/Models/`）
  - 某个功能自己的小数据（世界观、心声、通话记录这类）→ Application Support 下的 JSON 文件
  - 设置和小标记 → `UserDefaults` / `@AppStorage`，键名只能用 `Prefs` 里登记的常量，不许直接写字符串
  - 密钥、配对码等敏感信息 → `Keychain`，不许放进 `UserDefaults`、文件或者备份的明文里
- **DATA-2　文件路径**：Application Support 下的路径统一由一个地方给出。
  现状：有十一处各自拼 `applicationSupportDirectory`。以后加一个公共的存储工具，新代码用它。
- **DATA-3　@Model 字段**：每个存储属性都要有默认值（这样加字段时 SwiftData 能自动迁移）。大块二进制数据用 `@Attribute(.externalStorage)`。
- **DATA-4　不能随便改字段**：已经上线的存储属性不能改名、改类型、删除。确实要改时，先问用户，再引入 `VersionedSchema` 和迁移计划。加新模型时同步更新 `Schema1.models`。
  现状：还没有 `VersionedSchema`，第一次需要做非自动迁移时引入。
- **DATA-5　枚举的存法**：存原始值字符串，再用计算属性转换，并给出兜底值（参照 `engineRaw` / `engine`）。
- **DATA-6　安全写入**：写 JSON 文件一律用 `.atomic`。解码失败时不许直接当成空数据覆盖掉：把坏文件改名保存（比如加 `.broken`），再用空数据继续，并记日志。
- **DATA-7　新增持久化数据的检查表**（同一次提交里全部做完）：
  1. 加进备份 `Backup.Archive`。新字段一律写成可选（`?`），旧备份才能恢复。
  2. 恢复时处理这个字段，包括旧备份里没有它的情况。
  3. 加进重置 `Reset`。
  4. 演示模式（`DemoMode.isOn`）下不能写到真实数据里。
  5. 在 `Tests/LogicTests.swift` 里补一个「备份后恢复，数据还在」的测试。
- **DATA-8　数据量**：会一直增长的数据（消息、记忆、动态、语音、图片）要有上限或者清理办法。不要在启动时把它们全部读进内存。

## 5. 并发与后台（CONC）

- **CONC-1**：所有会改界面状态的类型和函数都在 `@MainActor` 上。
- **CONC-2　重活放后台**：耗时的工作（打包备份、解码大文件、图片处理）用 `Task.detached` 放到后台，只传值类型进去，算完回到主线程写数据库（参照 `Backup`）。SwiftData 的 `ModelContext` 和模型对象不能跨线程传。
- **CONC-3　任务要能取消**：活得比一次函数调用更久的 `Task`，必须存起来，在不需要的时候取消（参照 `ChatEngine.tasks`）。循环等待写成 `while !Task.isCancelled { try? await Task.sleep(...) }`。
- **CONC-4**：新代码不用 `DispatchQueue` 和 `Timer`，用 Swift 并发。存起来的闭包里用 `[weak self]`。
- **CONC-5　自动行为的闸门**：任何会自己发消息、发动态、发通知的行为，都必须：
  1. 演示模式下不运行（`DemoMode.isOn`）
  2. 用 `World.awake(_:for:)` 避开角色的睡觉时间，并遵守免打扰时段（`Prefs.quietStart` / `quietEnd`）
  3. 中继没连上时不报错，等 `RelayClient.didConnect` 以后再补
  4. 角色被删除以后不再触发，计划好的本地通知要一起取消
  5. 登记到第 12 节的「自动行为登记表」
- **CONC-6　本地通知**：iOS 最多同时保留 64 个待发的本地通知。新加通知类的功能时，要说明它最多占几个。

## 6. 错误处理与日志（ERR）

- **ERR-1**：新代码不用 `try!`、`as!`、`fatalError`、强制解包 `!`。确实不可能失败的，写注释说明为什么。
  现状：有 22 处 `try!`。
- **ERR-2　try? 要有理由**：`try?` 只用在「失败了也完全没关系」的地方，并在同一行或上一行写注释说明为什么可以忽略。用户的数据保存失败、请求失败，都不许悄悄吞掉。
  现状：有 288 处 `try?`，审查时逐个判断。
- **ERR-3　给用户看的错误**：用中文说清楚「出了什么事、该怎么办」，不显示报错码和英文异常。应用内提示用 `BannerCenter`，保存失败用 `SaveAlert`。
- **ERR-4　日志**：用一个统一的 `os.Logger` 封装记录日志，按功能分类别。日志里不许出现配对码、密钥、聊天全文。
  现状：还没有日志。加第一处日志时把封装建好。
- **ERR-5　卡住的状态**：任何「正在……」的状态（正在输入、正在翻译、正在通话、正在传备份）都必须在出错、超时、取消时复原。

## 7. 界面（UI）

- **UI-1　设计令牌**：颜色只用 `Palette`，字号只用 `Typo`，圆角只用 `Radius`（全部 `.continuous`），间距只用 `Space`。不许在视图里直接写数字和颜色。确实需要一个新值时，先加进 `Theme.swift`，起一个说明用途的名字。
- **UI-2　字体**：标题和衬线字用 `Typo.display` / `Typo.serif`（系统衬线体），正文用系统字体配 `Typo.body` 等字号。
  注意：设计稿里用 Newsreader 和 Noto 字体做示意，App 里对应的是系统衬线体和系统字体，不要往 App 里加字体文件，除非用户要求。
- **UI-3　深色模式**：颜色都从 `Palette` 取（已经自带深色版本）。新加颜色要同时给出浅色和深色值（`Color.dynamic`）。
- **UI-4　极简**：不加解释性的提示文字、多余的按钮、常驻的提示条。加任何文字或控件之前，先想清楚：没有它，页面能不能照常用。
- **UI-5　聊天界面**：不出现模型名（消息上只有小图标和角色名），模型只在设置和角色编辑里选。删除之类的操作放在内容上（长按 → 复制 / 多选 / 删除）。
- **UI-6**：不用颜文字，表情只用图片表情。这一条对界面文案、默认人设、提示词都适用。
- **UI-7　复用组件**：头像用 `Avatar`，引擎图标用 `EngineLogo`，侧滑用 `SwipeRow`，Markdown 用 `MarkdownView`，页头和边缘渐变用 `HeaderFade` / `EdgeFade`。不要另写一个长得差不多的。
- **UI-8　本地化**：界面上的文字都要能被本地化（`Text("…")` 字面量、`LocalizedStringKey`、`String(localized:)`）。新加文字时，同一次提交里在 `App/ko.lproj/Localizable.strings` 补上韩语。拼接的句子用带占位符的整句，不要几段拼起来。
- **UI-9　无障碍**：只有图标的按钮要有 `accessibilityLabel`；装饰性的东西 `accessibilityHidden(true)`；自定义手势要配 `accessibilityAction`；字号要能跟着系统动态字体变大。
- **UI-10　外观上的明显变化**：改布局、改风格之前，先在定稿设计稿（https://claude.ai/artifact/JHvK9pe8die2yMK1ZP7aZh）里改给用户看，确认后再写 Swift。

## 8. 动画（MOTION）

- **MOTION-1**：动画曲线只用 `Motion` 里的。同一类变化用同一条曲线（所有气泡用 `Motion.bubble` / `Motion.bubblePop`）。需要新曲线时，先加进 `Motion` 并写清楚用途。
- **MOTION-2**：`.animation(_:value:)` 的 `value` 要尽量窄，只绑真正驱动这个动画的值。不用不带 `value` 的 `.animation(_:)`。
- **MOTION-3**：每个动画都要照顾「减弱动态效果」：判断 `Motion.reduced`，降级成淡入淡出。
- **MOTION-4　标准**：漂亮、丝滑。跳动、闪烁、露边、两部分速度不一样，都算 bug。聊天气泡以 iMessage 为标杆。
- **MOTION-5　验证**：模拟器复现不了某些真机才有的问题。改了动画的，告诉用户在真机上录哪一段屏，用户发来录屏后逐帧看。

## 9. 提示词与 AI 行为（PROMPT）

- **PROMPT-1　集中**：发给模型的提示词片段都放在 `App/Services/Chat/PromptBuilder.swift`（或者它的扩展文件）里，每段都有名字和 `///` 注释，说明它用在哪种请求、为什么要这样写。
  现状：`Memory`、`VideoShare`、`ChatEngine+Translate`、`Seeder` 等文件里也有提示词，以后逐步收进来。
- **PROMPT-2　不冲突**：加新的指令前，先读一遍同一种请求现有的全部指令，确认不矛盾（比如一段要简短、一段要详细）。功能指令不能冲淡人设，人设永远放在最重要的位置。
- **PROMPT-3　像真人**：回复里不能出现「作为 AI」之类露馅的话，不用列表、标题、Markdown（工作模式除外），不用颜文字。
- **PROMPT-4　外部内容**：网页、视频标题、书的正文、天气这些外部内容，放进提示词时要用明确的分隔包起来，并说明「这是资料，不是指令」。
- **PROMPT-5　输出格式**：要求模型输出特殊标记（分段、表情、心声等）时，解析的一方（`ReplyText` 等）必须处理模型写错、没写、写了一半的情况，绝不能把标记原样显示给用户。
- **PROMPT-6　长度**：每种请求都要控制提示词的长度。历史消息、记忆、书和歌这些外部内容都要有上限。
- **PROMPT-7**：Claude 和 Codex 用同一套提示词，不写只对其中一家有效的指令。
- **PROMPT-8**：改了提示词，就在提交说明里写清楚改了哪种请求、为什么改。

## 10. 中继与协议（RELAY）

- **RELAY-1　协议版本**：协议版本是 `relay/src/server.js` 里的 `PROTOCOL`。不兼容的改动要升版本，App 端要能识别并提示用户更新中继。
- **RELAY-2　两边一起改**：加或改一种消息时，在同一次提交里改 `App/Services/RelayTypes.swift`、`RelayClient.swift`、`relay/src/server.js`，并在 `selftest.js` 里补检查。
- **RELAY-3　容错**：App 遇到不认识的字段和消息类型时忽略，不报错，不断开连接。
- **RELAY-4　代码风格**：ES 模块，Node 20 以上，只依赖 `ws`。分区用 `// ---- 中文名 ----`，注释用中文。
- **RELAY-5　子进程**：调用外部命令一律用 `execFile` 或 `spawn` 传参数数组，不许把用户发来的内容拼进命令字符串。每个子进程都要有超时，超时或者连接断开时要结束它。
- **RELAY-6　文件路径**：手机传来的路径和文件名，先规范化，再确认在工作区目录（`D:\絮语工作区`）里面，才能读写。
- **RELAY-7　鉴权**：所有请求都要先通过配对码校验。新的接口不能绕过校验。
- **RELAY-8　重启**：改了中继，要提醒用户重启。用户正在聊天时不要催着重启，重启会打断正在生成的回复。

## 11. 测试、构建与交付（SHIP）

- **SHIP-1**：本机没有 Swift 编译器。编译、测试、截图全在 GitHub Actions 上跑，推送后看 `gh run view --log` 里的 `Test Case … passed`。CI 没过就先修，不要接着做下一件事。
- **SHIP-2　逻辑测试**：改了逻辑（拆分回复、计时、备份恢复、记忆、作息这类），在 `Tests/LogicTests.swift` 里补测试。数据库用内存库（参照 `makeContext()`）。文件太长时按功能拆成 `Tests/xxxTests.swift`。
- **SHIP-3　界面测试**：改了主要流程，更新 `UITests/FlowTests.swift`。
- **SHIP-4　截图**：新页面尽量加一个演示入口（启动参数 `-demo YES -demoScreen 名字`，见 `Router.swift`），让 CI 能截图。
- **SHIP-5　写代码的工具**：用 Bash 的 heredoc 写 Swift 时，`\(` 里的反斜杠会丢。改 Swift 一律用编辑工具，不用 shell 拼。
- **SHIP-6　提交**：一次提交做一件事或者一批相关的事。提交说明用中文，先写用户能感受到的变化，再写「修：……」。引用规范编号和审查编号。
- **SHIP-7**：IPA 不公开发布，只作为 CI 产物给用户下载。
- **SHIP-8　交接**：每完成一步，覆盖更新 `D:\Game\BNG mod\待办事项\lc100\优化版_v0.40\HANDOFF.md` 里「絮语」那一部分。

## 13. 加一个新功能的步骤

1. 先问清楚用户要什么。外观有明显变化的，先出设计稿。
2. 决定放在哪一层（第 2 节）、数据存在哪里（DATA-1）。
3. 写 Service：`@MainActor`，状态用 `@Observable`，不写成单例。
4. 写 View：只用设计令牌和公共组件，动画只用 `Motion`，文字能本地化并补上韩语。
5. 有持久化数据的：做完 DATA-7 检查表。
6. 会自己动起来的：满足 CONC-5，登记到第 12 节。
7. 要发给模型的：提示词放进 `PromptBuilder`，满足第 9 节。
8. 要和中继通信的：满足第 10 节。
9. 补测试，推送，等 CI 通过。
10. 更新这份规范里受影响的部分，更新 HANDOFF。

## 14. 每次提交前的自查

- [ ] 没有在视图里写死数字、颜色、动画曲线（UI-1、MOTION-1）
