# 絮语工程规范

这份规范写给以后维护絮语的每一个 AI 和人。目标只有一个：任何人接手，都能按同一套写法改代码，改完不坏别的地方。

## 0. 怎么用

- 改絮语的任何代码之前，先读完这份规范。规则有编号（如 DATA-3），审查报告和提交说明里引用编号。
- 标着「现状」的是现在的代码还没做到的地方，括号里的 Z-xxx 是审查总清单（`D:\ai聊天app\絮语审查\总清单.md`）里对应的条目。新写的代码必须照规则写；碰到旧代码时，只在这次改动本来就要动的范围里顺手对齐，不要为了对齐规范去大面积改没让你改的代码。
- 规范和用户当面说的要求冲突时，以用户为准，并在同一次提交里更新这份规范（先问用户）。
- 规范没写到的情况：照着周围代码的写法来；拿不准就问用户，不要猜。

## 2. 架构分层（ARCH）

- **ARCH-1　依赖方向**：`Core` ← `Models` ← `Services` ← `Views`。下层不能引用上层的类型：Service 里不能出现 View 类型；Models 里不能调用 Service；Core 只能引用系统框架（Foundation、SwiftUI、UIKit 这类）。
  现状：`Router` 里用了 `DemoMode`、`Route.personaPage`，`Prefs.defaultModel(for: Engine)` 引用了 Models 的类型（Z-399、Z-457）。
- **ARCH-2　全局状态**：会被界面观察的服务，写成 `@MainActor @Observable final class`，在 `XuyuApp` 里创建一次，用 `.environment(...)` 注入（参照 `RelayClient`、`ChatEngine`、`Router`、`BannerCenter`）。不需要被观察的内部状态加 `@ObservationIgnored`。
- **ARCH-3　单例**：`static let shared` 只用于整个进程只能有一份的系统资源（音频播放、定位、App 锁这类）。新的业务服务不要再写成单例，用 ARCH-2 的注入方式。`enum` 里的 `static var` 缓存和状态也算单例。
  现状：`Books`、`Thoughts`、`MomentsEngine`、`ListenTogether`、`VideoCards`、`CallLogs`、`DiaryState`、`SaveAlert`、`ThoughtFont` 等是单例，以后重构时逐步改（Z-273）。
- **ARCH-4　无状态的逻辑**：只是一组函数、不持有状态的，写成 `enum Xxx { static func ... }`（参照 `ReplyText`、`Backup`）。
- **ARCH-5　界面里不写业务**：View 里只做展示、`@Query` 读取和简单的增删改。会连带撤通知、改别的数据的增删改不算「简单」，放进 Service。网络请求、拼提示词、计时、复杂的数据处理也都放进 Service。
  不要用固定的毫秒数去等系统动画收起再改数据，用 `onDismiss` 这类回调；确实要等的，用 `Motion` 里有名字的常量（Z-332、Z-411）。
- **ARCH-6　一个文件只做一件事**：一个文件放一个主要类型。同一个类型的不同功能用扩展拆开，文件名用 `类型+功能.swift`（参照 `ChatEngine+Recover.swift`）。
- **ARCH-7　文件和函数大小**：
  - 文件超过 500 行必须拆。300～500 行的不专门拆，以后改到它时顺手按功能拆开。新功能不要往已经超过 300 行的文件里塞，新开文件。
  - 函数（包括 View 的 `body`）超过 80 行，或者里面内嵌了别的函数，就拆成类型或扩展。
  现状：超过 500 行的 8 个文件排进第二批重构：`VoiceViews`、`ChatEngine`、`ChatView`、`VoiceCall`、`MomentsView`、`RelayClient`、`Composer`、`relay/src/server.js`（Z-458、Z-498）。`ChatEngine.reply` 约 250 行，另有 17 个函数或 body 超过 80 行，`CallSession.respond` 内嵌函数共享状态（Z-274、Z-412）。
- **ARCH-8　依赖库**：App 不引入第三方库；中继只依赖 `ws`。加任何依赖都要先问用户。
- **ARCH-9　业务数值**：时间间隔、频率、窗口、截断长度、上限这类业务数值放进 `Core/Limits.swift`，按功能分组，起说明用途的名字。提示词的长度预算放在 `Limits.Prompt`（见 PROMPT-6）。
  现状：还没有 `Limits.swift`，数值散在各文件里（Z-327、Z-489）。

## 3. 命名与注释（NAME）

- **NAME-1**：标识符用英文，遵守 Swift API Design Guidelines。类型用大驼峰，其余用小驼峰，布尔值读起来像判断（`isGroup`、`canWork`）。
- **NAME-2**：注释用中文。每个类型、每个含义不明显的属性和函数，都要有 `///` 文档注释，说清楚它对用户意味着什么、为什么这样做，而不是复述代码（参照 `Persona` 的属性注释）。
- **NAME-3**：大分区用 `// MARK: - 中文名`，同一分区里的小节用 `// MARK: 中文名`（不带横线）。
- **NAME-4**：改了代码就同步改注释。过时的注释比没有注释更坏。
- **NAME-5　选项用枚举**：有几种取值的设置，用 `enum Xxx: Int` 或 `enum Xxx: String`，不要用裸的 `Int` 或字符串编码。
  现状：`proactiveFreq`、`followUp`、`voiceFreq`、`momentsFreq` 用 `Int` 加注释表示；`Attachment.kindRaw`、`Persona.language`、`Persona.voiceProvider` 用裸字符串；`discussRounds` 的 -1、背景选择的 -1 是特殊值（Z-455）。新代码不要照抄，旧的在动到时改成枚举的计算属性（存储字段不变，见 DATA-4）。
- **NAME-6　术语**：同一个东西在代码、界面、注释里用同一个名字，以界面上的叫法为准：
  - 角色（整个角色）、人设（编辑角色里填的、TA 要了解的那段自我设定，不指整个角色）、动态（Moments）、世界观（World）、心声、一起听、一起读、约定、中继（「电脑中继」只用在设置里那一行的名字上）。
  - 界面里站在 TA 的角度说到用户时，叫「你」。
  - 分区标题和装饰字可以用英文（Today、Chats、Moments、Good morning、To do / Plans / Done、小组件的 us / today、Listening with、Voice call 这一类）；按钮、提示、说明、错误一律中文。
  - 默认角色就叫「Claude」「Codex」，这是角色名，不受 UI-5 限制。

## 4. 数据与持久化（DATA）

- **DATA-1　存在哪里**：
  - 用户内容和互相有关联的数据 → SwiftData（`App/Models/`）
  - 某个功能自己的小数据（世界观、心声、通话记录这类）→ Application Support 下的 JSON 文件，经 `Storage` 读写（DATA-2）
  - 设置和小标记 → `UserDefaults` / `@AppStorage`，键名只能用 `Prefs` 里登记的常量，不许直接写字符串。有默认值的键，默认值只写一处（`Prefs.defaults`，启动时 `register(defaults:)`），`@AppStorage` 的初值和服务里的读取都引用它；说明文字里的钟点、份数也从同一个常量拼出来
  - 密钥、配对码等敏感信息 → `Keychain`，不许放进 `UserDefaults`、文件或者备份的明文里。钥匙串项一律用 `…ThisDeviceOnly`，不随 iCloud 钥匙串和设备备份迁移；恢复出厂时显式删除
  现状：默认值在 `@AppStorage` 和服务里各写一遍（Z-406）；钥匙串项没有限定本机（Z-478）。
- **DATA-2　公共存储工具**：Application Support 下的读写统一经过 `Core/Storage.swift`：它给出路径、做原子写、解码失败时把坏文件改名 `.broken` 并记日志。按消息 ID 存的小数据用 `KeyedFileStore`，单张图片用 `ImageFileStore`。存储工具能注入根目录，测试和演示模式用临时目录（DATA-7 第 4 条、SHIP-2）。
  现状：还没有 `Storage.swift`，有十一处各自拼 `applicationSupportDirectory`（Z-456）。
- **DATA-3　@Model 字段**：每个存储属性都要有默认值（这样加字段时 SwiftData 能自动迁移）。大块二进制数据用 `@Attribute(.externalStorage)`。
- **DATA-4　不能随便改字段**：已经上线的存储属性不能改名、改类型、删除。确实要改时，先问用户，再引入 `VersionedSchema` 和迁移计划。加新模型时同步更新 `Schema1.models`。
  现状：还没有 `VersionedSchema`，第一次需要做非自动迁移时引入。
- **DATA-5　枚举的存法**：存原始值字符串，再用计算属性转换，并给出兜底值（参照 `engineRaw` / `engine`）。
- **DATA-6　安全写入**：写 JSON 一律原子写，不论写进文件还是 `UserDefaults`。解码失败时不许直接当成空数据覆盖掉：把坏数据改名保存（文件加 `.broken`），再用空数据继续，并记日志。
  `Codable` 结构加新字段时，手写 `init(from:)` 用 `decodeIfPresent(...) ?? 默认值`，或者把字段写成可选（合成的解码不认属性默认值，旧数据会整份解码失败）。
- **DATA-7　持久化数据登记表**：每一项持久化数据在 `Storage` 里登记一次，写明：进不进备份、哪一档重置清掉、删角色和删消息时怎么清。`Backup`、`Reset` 和删除都从登记表遍历，不各写一份清单。新增一项持久化数据时，同一次提交里全部做完：
  1. 登记，并加进备份 `Backup.Archive`。新字段一律写成可选（`?`），旧备份才能恢复。JSON 文件里的新字段同理（DATA-6）。
  2. 恢复时处理这个字段，包括旧备份里没有它的情况。图片文件和指向它的设置键同进同出：恢复时只有键、没有文件，就退回默认。
  3. 加进重置 `Reset`。
  4. 演示模式（`DemoMode.isOn`）下不能读写真实数据：SwiftData 用内存库，`UserDefaults` 用单独的 suite 且每次启动清空，Application Support 的小文件由 `Storage` 指向临时目录。
  5. 在测试里补一个「备份后恢复，数据还在」的测试。
  现状：备份、重置、删除各有一份清单，互相对不上（Z-400、Z-490、Z-036、Z-207、Z-181）；演示模式会读写真实数据（Z-502、Z-340）。
- **DATA-8　数据量**：会一直增长的数据（消息、记忆、动态、语音、图片）要有上限或者清理办法，不要在启动时把它们全部读进内存。
  - 会增长的列表（动态、相册、搜索结果、声音列表）用 `LazyVStack` / `LazyVGrid`；动态可以分段加载，滑到底再加载更早的。聊天页不用懒加载是有意的（只排版最近 120 条），这个例外写在 `ChatView` 的注释里。
  - 备份本身也算：打包和恢复不能把整份数据一次放进内存，大的二进制逐个读写。电脑上的备份要有总大小上限。电脑工作区里本来就有的文件（工作模式发回的文件），备份里不再存一份。
  - 备份不加密（用户定），但不许把密钥、配对码写进去（DATA-1）。

## 5. 并发与后台（CONC）

- **CONC-1**：所有会改界面状态的类型和函数都在 `@MainActor` 上。新类型要显式标 `@MainActor` 或者写成 `actor`，不许新增 `nonisolated(unsafe)`。Service 里接收 `@Model` 对象或 `ModelContext` 的 async 函数必须标 `@MainActor`。
  现状：`SWIFT_STRICT_CONCURRENCY` 是 `minimal`，按计划在第二批升到 `complete`（Z-499、Z-167、Z-468）。
- **CONC-2　重活放后台**：耗时的工作用 `Task.detached` 放到后台，只传值类型进去，算完回到主线程写数据库（参照 `Backup`）。SwiftData 的 `ModelContext` 和模型对象不能跨线程传，要放后台的先拷成值类型。
  - 必须放后台的：照片缩小、附件转 base64、拼大 JSON、解析大消息、图片解码。
  - 图片一律按显示尺寸解码：`cachedImage` 的 `maxPixel` 按「显示点数 × 屏幕倍数」传，不给默认值；`body` 里不许直接 `UIImage(data:)`。
  现状：Z-081、Z-082、Z-165、Z-125、Z-044。
- **CONC-3　任务要能取消、取消不当成功**：活得比一次函数调用更久的 `Task`，必须存起来，在不需要的时候取消（参照 `ChatEngine.tasks`）。循环等待写成 `while !Task.isCancelled { try? await Task.sleep(...) }`。
  - 被取消的请求不能当成成功：`relay.complete` 被取消时必须抛错，半截文字不许当完整回复存下。
  - `await` 回来、写数据库之前，先确认对象还在、条件仍然成立（这期间你说过话、已经有别的计划消息、角色或对话已删，就丢掉结果）。
  现状：Z-020、Z-164、Z-034。
- **CONC-4**：新代码不用 `DispatchQueue` 和 `Timer`，用 Swift 并发。存起来的闭包里用 `[weak self]`。
- **CONC-5　自动行为的闸门**：任何会自己发消息、发动态、发通知的行为，都必须：
  1. 演示模式下不运行（`DemoMode.isOn`）。
  2. 避开角色的睡觉时间和免打扰时段（`Prefs.quietStart` / `quietEnd`）：统一用 `World.deliverable(_:for:)`——先推到 TA 醒来，再查免打扰，推迟后的时间再过一遍两项检查，直到都满足。只用 `World.awake` 不保证避开免打扰。例外：约定（你和 TA 说好的时间）照原时间发，再忙也发。
  3. 中继没连上时不报错，等 `RelayClient.didConnect` 以后再补。
  4. 角色被删除以后不再触发，计划好的本地通知要一起取消（见 CONC-9）。
  5. 你先开口时（发消息、拍一拍、打电话），统一走一个入口撤掉这位角色还没到点的计划消息和晚回（约定除外）。
  6. 提前写好、到点才出现的消息，到点时在界面上和普通回复一样：聊天列表重排、算未读、出横幅或通知。排序和未读按「已经出现的最后一条消息」算，不靠生成时改 `updatedAt`。
  7. 「TA 此刻能不能开口」（睡觉、在忙、晚回中）由一个函数给出（`HumanTouch.availability(_:)`），单聊、群聊、一起听插话、动态点赞评论、回拍、通话接听都先问它，跨聊天、跨功能一致。通话：在忙可以不接；睡着时有一定概率接，但不秒接。
  8. 登记到第 13 节的「自动行为登记表」。
  现状：还没有 `World.deliverable` 和 `HumanTouch.availability`（Z-114、Z-314、Z-305、Z-190、Z-202、Z-309、Z-442）；到点消息不重排（Z-007）。
- **CONC-6　本地通知**：iOS 最多同时保留 64 个待发的本地通知。
  - 新加通知类的功能时，在第 13 节的登记表里写明它最多占几个。数量不封顶的来源（待办、约定）由一个统一的「重排」函数按时间只排最近的若干个，回前台时调用（Z-166）。
  - 和某条消息同时出现的一次性通知，用按绝对时间的 `UNTimeIntervalNotificationTrigger`；只有每天重复的提醒用日历触发（Z-152）。
- **CONC-7　音频**：`AVAudioSession` 的类别、激活和停用集中在一个协调器里。每个用音频的功能都处理打断和线路变化。会独占麦克风或扬声器的功能（通话、语音输入、复刻录音）开始前，先停掉其他正在用音频的功能。
  现状：各功能自己设音频会话（Z-208、Z-084、Z-023、Z-184、Z-159）。
- **CONC-8　后台常驻**：`beginBackgroundTask` 的到期处理器里必须同步调用 `endBackgroundTask`，不在处理器里再起 `Task`。会让 App 在后台常驻的东西要写明什么时候结束：一起听由你手动关；语音通话在后台继续，直到挂断；10 分钟一次的刷新在 App 后台活着时也照跑。
  现状：Z-123、Z-027。
- **CONC-9　删除和清空的统一收尾**：删除角色、清空聊天、删除群聊、重置都调用同一个收尾函数：停掉这个对话的所有任务（包括晚回、补一句、记忆整理），撤掉相关的计划消息和通知（包括约定）。不许在视图里自己 `context.delete` 消息。
  - 删除角色：TA 的记忆一起清。
  - 清空聊天：只清聊天，记忆留着；删掉的消息连同它们的通知一起撤，之后 TA 照常主动找你，通知和聊天要对得上。
  现状：Z-203、Z-033、Z-034。

## 6. 错误处理与日志（ERR）

- **ERR-1**：新代码不用 `try!`、`as!`、`fatalError`、强制解包 `!`。确实不可能失败的，写注释说明为什么。
  现状：22 处 `try!` 要补「为什么不会失败」的注释，另有 6 处强制解包；`as!` 和 `fatalError` 0 处（Z-403）。
- **ERR-2　try? 要有理由**：`try?` 只用在「失败了也完全没关系」的地方，并在同一行或上一行写注释说明为什么可以忽略。用户的数据保存失败、请求失败，都不许悄悄吞掉。从相册、相机、文件读取用户选的图片或文件失败也不许吞，至少告诉用户有几张没读出来。
  现状：有 288 处 `try?`，只有 15 处有注释（分类见审查 R11 附录 A），审查时逐个判断（Z-403、Z-070）。
- **ERR-3　给用户看的错误**：用中文说清楚「出了什么事、该怎么办」，不显示报错码和英文异常，也不出现 claude / codex 等模型名和「换另一个模型」。应用内的轻提示用公共 `Toast` 组件，收到消息的横幅用 `BannerCenter`，保存失败用 `SaveAlert`。
  - 请求失败时，不能把失败提示当成回答存进聊天、通话记录、书的问答。通话里可以保留角色口吻（比如「信号不太好」），但必须同时给出真实原因和重试办法。
  现状：还没有 `Toast` 组件（Z-300、Z-417）；失败提示被当成回答存下（Z-177）。
- **ERR-4　日志**：用一个统一的 `os.Logger` 封装记录日志，按功能分类别。日志和错误信息里不许出现配对码、密钥、聊天全文。唯一例外：中继窗口的启动横幅可以显示配对码（用户要抄写）。
  现状：App 里还没有日志，第二批建好封装（Z-403）。
- **ERR-5　卡住的状态**：任何「正在……」的状态（正在输入、正在翻译、正在通话、正在传备份）都必须在出错、超时、取消时复原。

## 7. 界面（UI）

- **UI-1　设计令牌**：不许在视图里直接写数字和颜色。在令牌上做加减（`Radius.card + 2`、`Space.page - 4`）等于写死。确实需要一个新值时，先加进 `Theme.swift`，起一个说明用途的名字。
  - 颜色只用 `Palette`，字号只用 `Typo`（设置行用 `Typo.rowTitle` 16、`Typo.value` 14），圆角只用 `Radius`（全部 `.continuous`；`Radius.sheet` 是系统 sheet 的圆角，加号和表情面板顶部用 `Radius.panel` 26），间距只用 `Space`，阴影只用 `Shadow`（card / float / lift），头像尺寸用 `AvatarSize`，图标字号用 `Icon`。
  - 列表行最小高度用 `Space.row` / `Space.rowTall`；按钮、输入框这类控件的高度用 `Space.control`（44，点按下限，和设计稿输入栏一致）。
  - 两类合理例外：压在照片上的控件、固定深色的全屏页（通话页）可以不跟深浅色变，但也要用命名令牌（`Palette.onPhoto`、`Palette.onPhotoScrim`、`Palette.callNight` 这类），不许在视图里写 `.white`、`Color(hex:)`。
  现状：`.system(size: 数字)` 259 处、`.padding(数字)` 152 处、视图里写死的颜色 80 处；`Shadow`、`AvatarSize`、`Icon`、`Radius.panel`、`Typo.rowTitle` / `value` 还没有，`Space.control` 还是 42（Z-046、Z-094、Z-100、Z-289、Z-047）。
- **UI-2　字体**：标题和衬线字用 `Typo.display` / `Typo.serif`（系统衬线体），正文用系统字体配 `Typo.body` 等字号。
  - 系统衬线体没有中文字形，中文会退回苹方；斜体只对拉丁字母有效。中文要衬线时，做成「字体选项」：像心声手札体那样下载系统自带的字体，由用户在设置里选。
  - 设计稿里用 Newsreader 和 Noto 字体做示意，App 里对应的是系统衬线体和系统字体。不要往 App 里打包字体文件，除非用户要求。
- **UI-3　深色模式**：颜色都从 `Palette` 取（已经自带深色版本）。新加颜色要同时给出浅色和深色值（`Color.dynamic`）。
  - `Palette.noir` 在深色下反转成浅色块是有意的反色强调；拍立得白边在深色下保持纯白。
  - 不分深浅的固定色（`avatarTints`、`clay`）必须在深色背景上验证对比度，最深的头像底色在深色下要有看得见的描边。`ink` 在深色下接近白色，用它做填充（开关轨道、选中环、实心按钮）时，要检查上面的白色元素还看得见。
  - 按背景强制深色或浅色的页面（聊天背景），要同时检查 UIKit 包装视图、系统菜单、键盘和从这一页弹出的 sheet；背景色也必须是 `Palette` 令牌。
- **UI-4　极简**：不加解释性的提示文字、多余的按钮、常驻的提示条。加任何文字或控件之前，先想清楚：没有它，页面能不能照常用。
- **UI-5　聊天界面**：不出现模型名（消息上只有小图标和角色名），模型只在设置和角色编辑里选。默认角色名「Claude」「Codex」不算模型名（NAME-6）。删除之类的操作放在内容上（长按 → 复制 / 多选 / 删除）。
- **UI-6**：不用颜文字，表情只用图片表情。这一条对界面文案、默认人设、提示词都适用。
- **UI-7　复用组件**：已有的公共组件必须复用，不要另写一个长得差不多的：头像 `Avatar`、引擎图标 `EngineLogo`、侧滑 `SwipeRow`、Markdown `MarkdownView`、页头和边缘渐变 `HeaderFade` / `EdgeFade`、页面大标题 `PageTitle`、子页面页头 `SubpageHeader`、开关 `InkToggle`、圆形图标按钮 `CircleIconButton`、设置行 `SettingRow`、分隔线 `Hairline`、设置页和分组 `SettingsPage` / `SettingsGroup`、统一的 sheet 修饰器（`Radius.sheet` + 纸色背景）。
  - 待建，建好后同样必须复用：`BackButton`、`.softCard()`、`NavRow`、`Toast`。
  - 注释里写着「和 X 同一种样子」的，就直接用 X 的组件。
  现状：Z-089、Z-096、Z-101、Z-343、Z-353、Z-355、Z-409。
- **UI-8　本地化**：界面上的文字都要能被本地化。新加文字时，同一次提交里在 `App/ko.lproj/Localizable.strings` 补上韩语；删功能时同一次提交删掉 ko 里的键。韩语界面目前没人用，韩语相关的问题一律排最低优先级。
  - 只有字面量、`LocalizedStringKey`、`String(localized:)` 会查表。`String` 变量、拼出来的字符串、`? :` 有一边是变量时传给 `Text`，都不会查表。
  - 公共组件的文字参数用 `LocalizedStringKey`，区分「固定文案」和「内容」。用户内容（名字、消息）用 `Text(verbatim:)`。要进界面的 `String` 在产生的地方就 `String(localized:)`。
  - 写进数据库的默认名，写入时按当前语言取。服务层和中继不产生直接给用户看的句子。
  - 拼接的句子用带占位符的整句，不要几段拼起来。
  现状：约 60 处 `String` 变量传给 `Text`（Z-464、Z-413、Z-473、Z-361、Z-243）。
- **UI-9　无障碍**：
  - 只有图标的按钮要有 `accessibilityLabel`；装饰性的东西 `accessibilityHidden(true)`；自定义手势要配 `accessibilityAction`。
  - 自己画的选择控件加 `.isSelected`，开关类按钮要有 `accessibilityValue`；只用颜色表示的状态也写进 `accessibilityValue`；滑杆读出的数值和屏幕上显示的一致。

  - 按钮里不能再放按钮。
  - `Palette.faint` 只用于装饰和不可用状态，要读的小字最浅用 `inkSoft`。
  - 字号固定用 `Typo`，不跟系统动态字体变大（用户定，Z-019 不改）。

- **UI-11　收起键盘**：每个能输入的页面都要能收起键盘。滚动视图用 `.scrollDismissesKeyboard(.interactively)`；没有滚动的单页，点空白处收起。多行输入框不能是收键盘的唯一出口。不为收键盘另加按钮（UI-4）。现状：Z-179。
- **UI-12　日期和时间**：界面上的时间一律英文 12 小时制（`Fmt.bubble` 这一种，形如 5:23 PM，像 iMessage），不分 Today、动态还是气泡。`Fmt.time24`、`full`、`day`、`duration` 只用于发给模型的文字。英文日期只用于分区标题和装饰字（NAME-6）。通话时长显示成「01:05」。

- **UI-13　body 里不做读写**：`body` 和它用到的计算属性里，不读钥匙串、不读文件、不解码 JSON、不查数据库、不新建 `DateFormatter` / `Regex`。需要的值在 `onAppear` / `.task` 里读进 `@State`，或者由 Service 缓存。现状：Z-168、Z-394、Z-337、Z-335。

## 9. 动画与触感（MOTION）

- **MOTION-1**：动画曲线只用 `Motion` 里的。同一类变化用同一条曲线：气泡和评论的出现、消失用 `Motion.bubble` / `Motion.bubblePop`；面板和提示条用 `Motion.spring`；按下和松开用 `Motion.pressIn` / `Motion.pressOut`。需要跟手势速度的曲线写成函数（如 `Motion.swipe(velocity:)`）。需要新曲线时，先加进 `Motion` 并写清楚用途。
- **MOTION-2**：`.animation(_:value:)` 的 `value` 要尽量窄，只绑真正驱动这个动画的值。不用不带 `value` 的 `.animation(_:)`。
- **MOTION-3　减弱动态效果**：位移、缩放、旋转、模糊、`matchedGeometryEffect`、循环动画都算「动」。打开「减弱动态效果」时，这些一律降级成原地淡入淡出。转场统一用 `Motion` 里的转场工厂，工厂内部读 `accessibilityReduceMotion`。现状：Z-416、Z-248。
- **MOTION-4　标准**：漂亮、丝滑。跳动、闪烁、露边、两部分速度不一样，都算 bug。聊天气泡以 iMessage 为标杆。
- **MOTION-5　验证**：模拟器复现不了某些真机才有的问题。CI 里的 `motion.mp4` 是可变帧率的录屏，只能查每一帧的状态，不能判断丝不丝滑。改了动画的，告诉用户在真机上录哪一段屏，用户发来录屏后逐帧看。`DemoMotion` 要覆盖键盘、加号面板、长按删除、多选删除、心声展开这几段。
- **MOTION-6　触感**：一律用 `.sensoryFeedback`，挂在不会随内容重建的视图上。只在你自己做了一个动作并且成功、或者需要你注意时震，同一个动作只震一次。发消息、发表情不震（像 iMessage）。现状：Z-246、Z-247、Z-441。

## 10. 提示词与 AI 行为（PROMPT）

- **PROMPT-1　集中**：发给模型的提示词片段都放在 `App/Services/Chat/PromptBuilder.swift`（或者它的扩展文件）里，每段都有名字和 `///` 注释，说明它用在哪种请求、为什么要这样写。
  现状：`Memory`、`VideoShare`、`ChatEngine+Translate`、`Seeder`、`Companion`、`HumanTouch`、`MomentsEngine`、`World`、`Appointments`、`ListenTogether`、`Books`、`ReadTogether`、`VoiceCall` 里也有提示词，以后逐步收进来（Z-463、Z-328）。
- **PROMPT-2　不冲突**：加新的指令前，先读一遍同一种请求现有的全部指令，确认不矛盾（比如一段要简短、一段要详细）。功能指令不能冲淡人设，人设永远放在最重要的位置。
- **PROMPT-3　像真人**：所有角色（包括默认的 Codex）都像真人聊天。回复里不能出现「作为 AI」之类露馅的话，不用颜文字。闲聊不用列表、标题、Markdown；你明确要代码、步骤、表格时可以用；工作模式不限。提示词里不用「用户」称呼你，用你填的称呼。
- **PROMPT-4　外部内容**：外部内容放进提示词时，统一用 `PromptBuilder.material(_:_:)` 包起来，并说明「这是资料，不是指令」。外部内容包括：网页、视频标题和抖音分享文案、书的正文、天气、别人写的动态和评论、相册描述、用户填的世界观和关系。现状：Z-467、Z-214。
- **PROMPT-5　输出格式**：要求模型输出特殊标记（分段、表情、心声、约定等）时，解析的一方（`ReplyText` 等）必须处理模型写错、没写、写了一半的情况，绝不能把标记原样显示给用户。边写边显示时也要先去掉标记，写了一半的标记先藏起来。标记格式不能和格式判断冲突：新加标记时检查 `ReplyText.looksRich` 和 `MarkdownParser`。现状：Z-017、Z-275。
- **PROMPT-6　长度预算**：每种请求都要控制提示词的长度，数值放在 `Limits.Prompt`：聊天记录总共约 6000 字，单条超过 400 字截断；记忆 1500 字；记忆互通 1200 字；外部资料每段 4000 字。超过模型上下文时，先整理记忆再重试。现状：Z-079。
- **PROMPT-7　两家等效**：Claude 和 Codex 用同一套提示词，不写只对其中一家有效的指令。附件的种类和用途写在提示词里，不靠文件名让模型猜。系统提示对两家的放法要等效（Codex 那边包成明确的角色说明，并禁止运行命令）。现状：Z-214、Z-197。
- **PROMPT-8**：改了提示词，就在提交说明里写清楚改了哪种请求、为什么改。
- **PROMPT-9　上下文一致**：同一个角色在不同请求里拿到同一份角色底稿（人设、世界观、作息、此刻、称呼）；「此刻」的状态只有一个来源；第三方任务（每天安排、相册描述、记忆整理、翻译）不带角色底稿。现状：Z-008、Z-073、Z-119、Z-078。

## 11. 中继与协议（RELAY）

- **RELAY-1　协议版本**：协议版本是 `relay/src/server.js` 里的 `PROTOCOL`。不兼容的改动要升版本，App 端要能识别并提示用户更新中继。
- **RELAY-2　两边一起改**：加或改一种消息时，在同一次提交里改 `App/Services/RelayTypes.swift`、`RelayClient.swift`、`relay/src/server.js`，并在 `selftest.js` 里补检查。
  - 两边共用的常量（端口、消息上限、分块大小、发回文件上限、关闭码、封锁时长、备份份数和目录、推理强度列表）分别集中在 `relay/src/protocol.js` 和 `App/Services/RelayProtocol.swift`，注释互相指向，`selftest` 核对两边一致。App 不靠错误文字判断协议状态。
  现状：常量散在两边各处（Z-491）。
- **RELAY-3　容错**：App 遇到不认识的字段和消息类型时忽略，不报错，不断开连接。
- **RELAY-4　代码风格**：ES 模块，Node 20 以上，只依赖 `ws`。分区用 `// ---- 中文名 ----`，注释用中文。
  现状：只有 `server.js` 有分区注释，`engines.js`、`gate.js`、`config.js`、`resolve.js` 没有，拆 `server.js` 时一起补（Z-500）。
- **RELAY-5　子进程**：调用外部命令一律用 `execFile` 或 `spawn` 传参数数组，不许把用户发来的内容拼进命令字符串。每个子进程都要有超时。用户取消或超时时结束它；连接断开不结束（回复要能取回）。Windows 上结束整棵进程树（`taskkill /T /F`），提前收尾以后仍保留兜底超时。现状：Z-219。
- **RELAY-6　文件路径**：手机传来的路径和文件名，先规范化、解析符号链接，再确认在工作区目录（config 里的 `workDir`）里面，才能读写。AI 工具调用的路径同样处理。改变 AI 权限或指令的文件（`.claude/`、`.mcp.json`、`CLAUDE.md`、`AGENTS.md`、`.codex/` 这类）AI 不能写。App 收到的文件名也要清理成单纯的文件名（去掉路径和 `..`）。现状：Z-005、Z-039、Z-218。
- **RELAY-7　鉴权**：所有请求都要先通过配对校验，新的接口不能绕过。配对码不在网络上明文传输，用挑战-应答；App 先确认对方是自己的中继，才发内容；执行命令的请求（工作模式、确认）必须能证明来自已配对的手机。现状：Z-004、Z-038、Z-481。
- **RELAY-8　重启**：改了中继，要提醒用户重启。用户正在聊天时不要催着重启，重启会打断正在生成的回复。
- **RELAY-9　不崩溃**：每个 WebSocket 连接都挂 `error` 监听；进程有 `uncaughtException` / `unhandledRejection` 兜底；启动脚本在中继异常退出后自动重启。现状：Z-003、Z-221、Z-484。
- **RELAY-10　工作模式的把关**：工作模式的把关（手机确认、只在工作区里、不能改权限文件）对所有引擎都必须生效。新引擎没有等价的确认机制，就不能接入工作模式。现状：Codex 不经把关（Z-002）。

## 14. 加一个新功能的步骤

1. 先问清楚用户要什么。外观有明显变化的，先出设计稿。
2. 决定放在哪一层（第 2 节）、数据存在哪里（DATA-1）。
3. 写 Service：`@MainActor`，状态用 `@Observable`，不写成单例。
4. 写 View：只用设计令牌和公共组件，动画只用 `Motion`，文字能本地化并补上韩语。
5. 有持久化数据的：登记并做完 DATA-7。
6. 会自己动起来的：满足 CONC-5，登记到第 13 节。
7. 要发给模型的：提示词放进 `PromptBuilder`，满足第 10 节。
8. 要和中继通信的：满足第 11 节。
9. 补测试，推送，等 CI 通过。
10. 更新这份规范里受影响的部分，更新 HANDOFF。
